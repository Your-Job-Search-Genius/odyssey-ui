# Writesea Odyssey UI — Agent Design and Implementation Guidelines

This document defines the design and implementation policy to supply through the Writesea Odyssey UI MCP. It applies to agents producing UI designs, component implementations, and application integrations. Select rules according to the task, use them before building, and verify the result before completion.

## Policy interpretation

- **Required standards and explicit preferences:** Meet applicable accessibility requirements and honor the user's stated technology and feature preferences. The contrast baseline is WCAG 2.2 AA. Passing this checklist alone does not prove complete WCAG conformance.
- **Flexible design direction:** Typography, spacing, layout, and motion guidance evaluates readability, relationships, usability, and consistency. Do not enforce example pixel values, universal breakpoints, fixed durations, font choices, or component counts.
- **Conditional features:** A checklist is not permission to add every feature. Sorting, bulk actions, tabs, modal navigation, persistence, offline mode, push, and background synchronization apply only when the task requires or authorizes them.
- **User instructions:** An explicit user instruction takes precedence over a default preference. Preserve established project decisions unless the user asks to change them. Identify material conflicts rather than silently claiming compliance.
- **Deliverable-aware verification:** A design can demonstrate composition and documented behavior. Working semantics, request counts, state transitions, rendering cost, storage, and installation require implementation evidence.

## Writesea Odyssey UI MCP integration

Supply this document as an available policy resource or relevant rule content in the MCP integration. The consuming agent must receive the policy before choosing components or generating code. Merely saving this file does not configure or technically enforce the MCP.

When Writesea Odyssey UI component metadata, examples, or documentation are available, inspect and reuse the supported components, tokens, and APIs. Do not invent component names, properties, accessibility guarantees, or tool capabilities. Evaluate the assembled interface against the rules even when each individual component comes from the library.

For a task, expose the shared baseline and applicable category rules rather than treating the checklist as an instruction to implement unrelated features. Where the MCP supports automated validation, map checks to observable evidence. Do not represent guidance-only or untested behavior as an automated pass.

## Required task workflow

1. Understand the user goal, deliverable, supported environments, existing stack, and relevant Writesea Odyssey UI capabilities. Clarify only unresolved information that materially changes the result.
2. Classify the components, interactions, data flows, and platform capabilities involved. Select all applicable categories before building.
3. Always include **Color contrast** and **Screen readers (NVDA)** for every UI task. Include shared accessibility, hierarchy, typography, responsive, spacing, and feedback rules wherever applicable.
4. Record intended structure, states, content, responsive behavior, state ownership, and any applicable cache or motion policy before implementation.
5. Build with the relevant checklists in view. Reuse suitable existing conventions; preserve the explicit defaults below.
6. Verify the delivered result against selected rule identifiers. Fix applicable failures and repeat affected checks.
7. Report completion only with accurate verification coverage. Unverified requirements remain unverified; do not silently turn them into Pass or Not applicable.

## Explicit defaults

- **State management:** Use an external state-management library. If no alternative is specified, default to Redux Toolkit, with React-Redux integration where applicable. This is a product preference rather than a universal claim that all applications require Redux.
- **Server data:** Use RTK Query with the Redux default where suitable. If TanStack Query is explicitly selected, it can own server-data queries and caching. Do not maintain competing query systems or duplicate authoritative data for the same flow.
- **API transport:** Prefer Axios where suitable; reuse an existing appropriate transport rather than installing a redundant client. Axios and query libraries have different responsibilities.
- **Rendering:** Prevent unnecessary renders. Preserve all required UI updates; never promise zero re-renders.
- **Caching:** Reuse data only where useful and permitted by freshness and lifecycle requirements. No universal cache lifetime or blanket persistence.
- **PWA:** Offline mode and PWA-specific caching are **off by default**. Enable offline content, service-worker response caches, precaching, offline persistence, queued writes, and background synchronization only when the user explicitly requests or specifies them. A request to build a PWA alone does not authorize those features. This does not automatically disable ordinary HTTP caching or an intentionally configured in-memory query cache.

## Verification and completion record

For each applicable rule, record one result:

- **Pass:** Evidence demonstrates the requirement or intended outcome.
- **Fail:** The result conflicts with an applicable requirement or the guideline's usability objective. Fix it and recheck.
- **Not applicable:** The behavior does not apply to this task; record why. Optional features that were not requested are not failures.
- **Not verified:** Evidence is unavailable or the deliverable cannot demonstrate the behavior; record the limitation and remaining check.

Use a compact record such as:

| Rule ID | Applicability / context | Result | Evidence or reason | Remaining action |
| ------- | ----------------------- | ------ | ------------------ | ---------------- |

Record the selected categories, explicit feature settings, and relevant environment coverage. Use real measurements where required, including contrast, network behavior, and rendering performance. Distinguish design review from implemented behavior. An installed dependency, a component name, or a screenshot alone is not verification.

Applicable hard requirements must not be reported as satisfied while they fail. Where verification is unavailable, provide an accurate limitation instead of an unconditional completion claim. Do not impose an approval step for routine reversible work already authorized by the user.

## Spacing and layout

Policy: spacing guidance must provide direction, not prescribe or enforce pixel values or a particular spacing scale. Preserve the product's existing spacing choices when they work. Evaluate the visible result: related elements are understandable, separate field groups have separation, and components do not accidentally touch or merge. Agents may choose appropriate values where none are defined. Do not fail a design merely because it uses a different value from an example.

### Principles and verification

| ID       | Rule                                                                                                                                                                                                       | Verification                                                                                                            |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| SPACE-01 | Follow existing spacing definitions where available; otherwise choose values suited to the design and keep similar relationships coherent. No particular scale or pixel value is required by this library. | Equivalent relationships look consistent and deliberate.                                                                |
| SPACE-02 | Use padding for space within a container or control, gap for siblings in a suitable layout, and margin for exterior separation when appropriate.                                                           | Each spacing property expresses the intended relationship.                                                              |
| SPACE-03 | Prefer parent ownership of sibling spacing and component ownership of internal padding.                                                                                                                    | Components remain reusable in different layouts; hidden exterior spacing does not accumulate.                           |
| SPACE-04 | Provide appropriate separation between a label and input, and between complete field groups. Keep strongly related content visually grouped.                                                               | Labels and inputs do not accidentally touch; adjacent field groups do not merge; labels clearly belong to their inputs. |
| SPACE-05 | Consider label spacing, field-group spacing, card padding, page gutters, and section spacing separately. Reuse existing definitions for those roles when available.                                        | No necessary spacing relationship is omitted merely because another relationship already has spacing.                   |
| SPACE-06 | Account for combined gap, margins, and padding at each boundary.                                                                                                                                           | No accidental double spacing; legitimate nested container padding is allowed.                                           |
| SPACE-07 | Adapt page gutters, container widths, and section spacing for supported screens.                                                                                                                           | Content remains usable on narrow screens and does not become unnecessarily stretched on wide screens.                   |
| SPACE-08 | Verify rendered spacing with actual text, wrapping, errors, zoom, and controls.                                                                                                                            | Content is not clipped and field-message grouping survives alternate states.                                            |
| SPACE-09 | Allow spacing values to vary when content, density, responsive layout, or optical alignment calls for it.                                                                                                  | Judge clarity, usability, and consistency in the rendered result rather than exact numeric conformity.                  |

### Relationships to inspect, without prescribed measurements

- Icon and its text: distinct, but visibly part of the same control.
- Label and its input: enough separation for readability, with clear association.
- Input and its helper/error: close enough to belong together, without crowding.
- Complete field group and the next: visibly separate; spacing inside a field does not replace spacing between fields.
- Heading and description: visually grouped, with clear hierarchy.
- Introductory content and the form: enough separation to distinguish the blocks.
- Last field and primary action: clear separation while retaining a connection to the form.
- Card boundary and content: intentional internal breathing room.
- Page boundary and content: usable edge clearance appropriate to the screen.
- Major sections: clearly distinguishable groups.

A field group includes its label, input, and any helper or error message. Internal spacing and space between groups have different roles. Control height, text line-height, and touch usability must be checked alongside padding; padding alone does not guarantee usable controls. Intentionally connected components, such as segmented controls, may touch when their design calls for it; accidental merging of unrelated fields is the problem.

Reference: [Carbon Design System: Spacing](https://www.carbondesignsystem.com/building-blocks/foundations/spacing/overview).

## Responsive design

Direction, not a prescribed set of device widths or breakpoints: preserve the user's task, readable content, and usable controls as available space changes. Reuse an existing responsive system when it works. Select layout transitions according to the content rather than device names alone. Representative checks provide evidence of adaptability; they cannot prove coverage of every possible screen.

| ID      | Guideline                                                                                                             | Verification                                                                                                                                                                                               |
| ------- | --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RESP-01 | Keep layouts usable with a mobile keyboard open and with limited available height.                                    | Focused fields, errors, and the primary action can be reached by appropriate scrolling; nothing is trapped below an inaccessible edge.                                                                     |
| RESP-02 | Handle long labels, names, entered values, translations, and error messages.                                          | Wrapping or an intentional accessible alternative prevents clipping, overlap, and unintended overflow.                                                                                                     |
| RESP-03 | Preserve usability when browser zoom or text size increases.                                                          | Content reflows and essential controls remain accessible without disabling zoom.                                                                                                                           |
| RESP-04 | Define supported environments and inspect narrow, intermediate, and wide widths, including resizable desktop windows. | Evidence includes representative sizes and widths around layout transitions, not just named device presets.                                                                                                |
| RESP-05 | Adapt composition to the available space rather than shrinking the entire desktop interface.                          | Columns, cards, and sidebars wrap, stack, move, or change presentation before becoming cramped.                                                                                                            |
| RESP-06 | Preserve important information and tasks at every supported layout.                                                   | Moving content into a menu or disclosure still gives users a discoverable way to access it; essential actions do not disappear.                                                                            |
| RESP-07 | Choose breakpoints where the content or interaction needs a layout change.                                            | Neither side of a transition has collisions, awkward compression, or excessive empty space; existing working breakpoint definitions may be reused.                                                         |
| RESP-08 | Avoid accidental horizontal page overflow; do not conceal the defect by clipping content.                             | Ordinary text and controls fit or reflow. No universal spacing numbers are prescribed.                                              |
| RESP-11 | Adapt navigation for the space available.                                                                             | Menus can be opened, navigated, and closed; destinations and current location remain understandable.                                                                                                       |

| RESP-18 | Verify delivered behavior at the appropriate level and report coverage accurately.                                    | Mockups show layouts and specified behavior; implementation checks include representative browsers and, when available, real touch/keyboard behavior. Unchecked environments are recorded as not verified. |

### Before building

Identify content priority, component-specific transformations, navigation changes, complex-content strategy, short-height and keyboard handling, and relevant rule categories. Choose representative test conditions and reuse existing product conventions where appropriate.

### After building

Resize through intermediate widths and around transitions. Check small and large content, narrow and wide viewports, short height, supported orientations, zoom/text enlargement, keyboard-open forms, alternate states, and supported input methods. Fix failures and repeat affected checks. Report what was verified and what remains unverified rather than claiming every possible device was tested.

References: [web.dev: Learn Responsive Design](https://web.dev/learn/design), [W3C WAI: Understanding Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html).

## Typography and content

Coverage includes headings, titles, subtitles, labels, and all other UI text. Define text according to its purpose, hierarchy, and context, rather than prescribing a universal font family, size, weight, line-height, or maximum number of lines. Use appropriate existing text styles when available. A role is conditional on need: this catalog is not a requirement to add every role to every screen.

## Color contrast — mandatory before and after every UI task

Policy: follow WCAG 2.2 and check color contrast both before creating any UI and after creating it. Use the AA contrast criteria as the baseline, including their actual applicability and exceptions. These minimum contrast thresholds are requirements, unlike the flexible numerical choices in spacing guidance. Passing contrast checks alone does not establish full WCAG 2.2 conformance.

### Thresholds

| Content                                                                                              | Minimum                     | Scope                                                                                                                                                                     |
| ---------------------------------------------------------------------------------------------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ordinary text and images of text                                                                     | 4.5:1                       | Includes labels, body text, button text, placeholders, helper/error messages, table text, badges, and tooltip text where applicable.                                      |
| Large-scale text and images of large-scale text                                                      | 3:1                         | At least 18 pt regular or 14 pt bold, or equivalent sizes for applicable scripts under the WCAG definition. Do not classify text as large solely because it is a heading. |
| Visual information needed to identify active controls, their states, or meaningful graphical objects | 3:1 against adjacent colors | Applies to the necessary identifying features, not automatically to every decorative border or every pair of state colors.                                                |

Text and essential non-text features of a control are assessed separately. Do not apply the large-text or non-text minimum to ordinary button text. Large text may still use 4.5:1 or higher; the lower threshold is an allowed minimum, not a design goal.

| CONTRAST-01 | Select this category for every UI task before design and again before completion.                   | Contrast is included in the task's verification record, even when existing components or tokens are reused.                                                                                                                                |
| CONTRAST-02 | Before building, identify intended foreground/background combinations and applicable thresholds.    | Text, surfaces, icons, control states, and supported themes have an explicit pairing plan; a palette alone is not counted as verified.                                                                                                     |
| CONTRAST-03 | Measure ordinary text contrast against its actual background at a minimum of 4.5:1.                 | Include secondary text, placeholders, error/helper messages, badges, table cells, and button labels; muted styling is not an exemption.                                                                                                    |
| CONTRAST-04 | Apply the 3:1 large-text minimum only when the actual size and weight qualify.                      | Responsive styles that reduce text below the large-text definition are checked at 4.5:1.                                                                                                                                                   |
| CONTRAST-05 | Check essential non-text control and graphical information at 3:1 against relevant adjacent colors. | Inputs, meaningful icons, selection cues, and chart information are identifiable; do not require every decorative line or fill to meet a control-identification threshold.                                                                 |
| CONTRAST-06 | Check all applicable states and supported themes.                                                   | Default, hover, keyboard focus, pressed, selected, loading, error, and light/dark themes are covered as applicable. Merely checking the default state is insufficient.                                                                     |
| CONTRAST-07 | Account for transparency, gradients, images, overlays, and changing surfaces.                       | Use the effective foreground/background pairing and the least favorable relevant background. A nominal token pair does not pass when its composited presentation fails.                                                                    |
| CONTRAST-08 | Verify the delivered styles after building, using measurement rather than visual judgment alone.    | Check the actual rendered size, weight, colors, opacity, and backgrounds. Use computed underlying colors for text rather than sampling anti-aliased letter edges.                                                                          |
| CONTRAST-09 | Compare measured ratios without rounding a failing value upward.                                    | A ratio below the applicable minimum remains Fail even if a rounded display looks like the threshold.                                                                                                                                      |
| CONTRAST-10 | Do not communicate meaning only through color.                                                      | Error, selected, status, and chart meaning have appropriate text, shape, pattern, icon, or other additional cues. Contrast alone does not satisfy this requirement.                                                                        |
| CONTRAST-11 | Keep authored keyboard-focus indicators visible and assess applicable non-text contrast.            | Focus can be located against relevant surroundings. Do not claim the separate WCAG 2.2 AAA Focus Appearance criterion is an AA requirement.                                                                                                |
| CONTRAST-12 | Apply genuine exemptions narrowly and record the reason.                                            | Inactive controls, purely decorative content, and qualifying logotypes may be exempt under the relevant criteria. Active helper text, secondary labels, and muted content are not classified as inactive simply to bypass contrast checks. |
| CONTRAST-13 | Record useful measurement evidence.                                                                 | For a tested combination, record element/state/theme, foreground and background, text size/weight where relevant, measured ratio, applicable threshold, and result. A mockup check does not establish implementation contrast.             |
| CONTRAST-14 | Fix failures and recheck affected combinations before claiming completion.                          | Changes to shared tokens are checked in their affected contexts. If measurement is unavailable, mark Not verified and report the limitation rather than assuming Pass.                                                                     |

## Screen readers (NVDA) — mandatory for every UI task

Policy: every interactive or informative UI must be usable with NVDA on Windows (Firefox and Chrome) in browse mode and focus mode. Prefer the native semantics the library components already provide over custom ARIA; the simplest correct structure wins. Static review and automated tools (axe) are supporting evidence only; without an actual NVDA run, record SR rules as Not verified.

| ID    | Rule                                                                                                                                                                                                                | Verification                                                                                                           |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| SR-01 | Every interactive control exposes a name, role, and state that NVDA announces correctly (for example "Save, button" or "Remember me, check box, not checked").                                                      | Tab through and arrow in browse mode with NVDA Speech Viewer on; each control is announced with name, role, and state. |
| SR-02 | Use library components and native semantics; add ARIA only to fill a real gap. Never set `role="application"` or ARIA that contradicts the native role.                                                             | The accessibility tree has no redundant or conflicting roles.                                                          |
| SR-03 | Form fields announce label, required state, current value, hint, and error on focus (label association, `aria-describedby`, `aria-invalid`).                                                                        | Tabbing into an invalid required field announces label, "required", "invalid entry", and the error text.               |
| SR-04 | Async feedback (submit errors, toasts, saved states, result counts, loading completion) is announced through a polite or assertive live region that exists before the update, without stealing focus unnecessarily. | Speech Viewer captures each message once, at the intended politeness.                                                  |
| SR-05 | Dialogs, drawers, sheets, and menus announce their name and role on open, move focus inside, contain it while modal, close on Escape, and return focus to the trigger.                                              | NVDA announces "<title>, dialog"; Escape closes; focus returns to the trigger.                                         |
| SR-06 | Headings form a logical outline (one h1, no skipped levels) and landmarks (main, navigation, banner, contentinfo) exist, so H, D, and NVDA+F7 navigation work.                                                      | NVDA Elements List shows a sensible heading and landmark outline.                                                      |

| SR-09 | Browse-mode reading order matches the visual order; no information exists only on hover; visually revealed content is reachable in browse mode.                                                                     | Arrow through the page; order and content match the screen.                                                            |
| SR-10 | Data tables use real table semantics with header cells, so NVDA announces row and column headers.                                                                                                                   | Ctrl+Alt+Arrow navigation announces headers.                                                                           |
| SR-11 | Composite widgets (combobox, tabs, grid, slider, listbox) follow the ARIA Authoring Practices pattern implemented by React Aria; NVDA switches to focus mode on them and Escape returns to browse mode.             | Arrow keys operate the widget; mode switching works.                                                                   |
| SR-12 | Record NVDA evidence: NVDA version, browser, and what was announced. Without an actual NVDA run, mark SR rules Not verified.                                                                                        | The completion record lists the NVDA environment, or Not verified with the remaining check.                            |

## Accessibility — shared baseline

- A11Y-01: Support keyboard use with a logical focus order and a visible focus indicator.
- A11Y-02: Expose labels, errors, and action feedback appropriately to screen readers.
- A11Y-03: Explain errors in text rather than relying on color alone.
- A11Y-04: Keep text readable against its background and controls easy to activate.
- A11Y-05: Verify screen-reader behavior with the **Screen readers (NVDA)** checklist; it is mandatory for every UI task.

## Visual hierarchy and consistency — shared baseline

- VIS-01: Make important information and the primary action easy to identify.
- VIS-02: Use consistent typography, spacing, colors, and control styling.
- VIS-03: Group related content and clearly separate unrelated sections.

## Feedback and recovery — shared baseline

- STATE-01: Show meaningful feedback while an action is processing.
- STATE-02: Prevent accidental duplicate submission while a request is pending.
- STATE-03: Explain success and the next step.
- STATE-04: Make retry or correction possible after failure; preserve useful entered information where appropriate.

## Buttons and actions

Provide direction through meaning, hierarchy, and behavior. Do not prescribe universal colors, dimensions, corner radii, padding, spacing values, or button positions. Reuse a suitable existing component system and judge whether users can identify, understand, activate, and recover from the action. Apply this category wherever interactive actions exist, including forms, tables, navigation triggers, dialogs, and drawers.

| ID        | Guideline                                                                                                                                                  | Verification                                                                                                                                                                                                           |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ACTION-01 | Distinguish actions from navigation. Use button semantics for operations and link semantics for navigating to a destination, even when styled as a button. | Users and assistive technology receive appropriate behavior; ordinary links preserve expected navigation capabilities.                                                                                                 |
| ACTION-02 | Prefer native semantic controls or an accessible established component.                                                                                    | The interaction is not merely a clickable visual container lacking keyboard and accessibility behavior.                                                                                                                |
| ACTION-03 | Use a concise label that communicates the outcome.                                                                                                         | Labels such as Save changes, Log in, or Delete record are understandable in context; vague words are used only when their meaning is already clear.                                                                    |
| ACTION-04 | Make hierarchy appropriate to each task or action group.                                                                                                   | The main next action is clear without making every action equally prominent. Do not impose an absolute one-primary-button-per-page rule on independent tasks.                                                          |
| ACTION-05 | Keep cancel, secondary, and destructive actions distinguishable.                                                                                           | Users can tell which action commits, dismisses, navigates, or destroys; distinction does not depend on color alone.                                                                                                    |
| ACTION-06 | Give controls usable size and intentional internal and external space.                                                                                     | Text, icons, and adjacent controls do not crowd or overlap; touch activation is comfortable and accidental neighboring activation is avoided. No universal pixel value is imposed.                                     |
| ACTION-07 | Keep actionable controls discoverable.                                                                                                                     | Essential actions are not available only on hover or through unexplained icons.                                                                                                                                        |
| ACTION-08 | Supply meaningful accessible names for icon-only buttons.                                                                                                  | The action and relevant record context are understandable; a tooltip may supplement but does not replace an accessible name.                                                                                           |
| ACTION-09 | Define applicable default, hover, focus, pressed, loading, disabled, and selected states.                                                                  | State differences are understandable and consistent; do not invent irrelevant states for a control.                                                                                                                    |

| ACTION-11 | Use disabling deliberately and explain unavailable actions when the reason is not apparent.                                                                | Users can discover the prerequisite without relying on a tooltip on an unfocusable disabled button. | ACTION-12 | Enforce disabled behavior, not merely disabled appearance.                                                                                                 | Pointer and keyboard activation cannot run an unavailable action; accessibility state matches behavior. | ACTION-15 | Give destructive or costly actions proportionate protection.                                                                                               | A clear consequence, confirmation, undo, or another suitable recovery strategy reduces accidental loss without requiring confirmations for every harmless action.                                                      |

| ACTION-18 | Adapt action groups responsively while retaining task meaning.                                                                                             | Long labels, narrow screens, zoom, wrapping, stacking, or overflow menus preserve discoverability, order, and usable spacing.                                                                                          |
| ACTION-19 | Verify the complete action flow.                                                                                                                           | Check keyboard and touch behavior, relevant states, rapid repeated activation, slow or failed requests, long labels, small screens, and focus after activation. ## Tabs and related views

Distinguish true tab-and-panel interfaces from navigation links styled as tabs and controls that filter the same dataset. Choose semantics according to behavior, not appearance. For example, Overview / Activity / Settings can be related panels; All / Active / Archived may instead be mutually exclusive status filters. Reuse suitable existing product patterns. No universal tab width, gap, color, orientation, or maximum count is prescribed.

| ID     | Guideline                                                                            | Verification                                                                                                                                                                                                                   |
| ------ | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| TAB-01 | Choose tabs for related content where viewing one panel at a time suits the task.    | Do not conceal information that users need to compare simultaneously, or use ordinary tabs to imply mandatory sequential steps.                                                                                                |
| TAB-02 | Give the group a coherent purpose and tabs clear, concise labels.                    | Users can predict each tab's content; labels are distinguishable even with long text or translation.                                                                                                                           |
| TAB-03 | Define the initial selected tab deliberately.                                        | Valid route or persisted state is honored when intended; otherwise an appropriate default is chosen rather than showing no selected panel.                                                                                     |
| TAB-04 | Make selection distinct from hover and keyboard focus.                               | The selected tab and visible panel match, with an accessible state and a visual cue beyond color alone.                                                                                                                        |
| TAB-05 | Associate every true tab with its panel and label the group appropriately.           | Tab-list, tab, panel, selected state, and accessible relationships describe the real interaction. Page navigation links are not assigned tab semantics merely for styling.                                                     |
| TAB-06 | Use appropriate keyboard behavior for a true tab interface.                          | Tab reaches the selected tab and then panel content; arrow keys move among tabs according to orientation. Manual activation uses Enter or Space. Do not apply this pattern indiscriminately to ordinary links or filters.      |
| TAB-07 | Choose automatic versus manual activation according to latency and interaction cost. | Automatic activation is suitable when panels appear without noticeable delay; manual activation avoids fetching or disrupting the view on every focus movement.                                                                |
| TAB-08 | Keep focus useful while changing tabs.                                               | Activating a tab ordinarily leaves focus on that tab; users can then enter the panel. Hidden panels do not leave hidden controls in the focus order.                                                                           |
| TAB-09 | Keep visual spacing and the relationship to the panel clear.                         | Labels and indicators do not collide, tabs remain distinguishable, and the group reads as belonging to its content without prescribed measurements.                                                                            |
| TAB-10 | Adapt overflow deliberately.                                                         | Scrolling, another orientation, or an appropriate alternative selector preserves access to all views; the selected or focused option is revealable and labels are not silently clipped.                                        |
| TAB-11 | Preserve entered work and useful per-panel context when switching where appropriate. | Switching does not silently discard drafts, selections, or filters. Shared and per-panel state are defined explicitly.                                                                                                         |
| TAB-12 | If multiple form sections are in tabs, handle errors in hidden panels.               | Submission can identify and reveal the tab containing an invalid field, and users can correct it without losing other input.                                                                                                   |
| TAB-13 | Define loading, empty, error, and retry behavior for each panel.                     | A failed load is not shown as no data; feedback belongs to the selected view and the next step is clear.                                                                                                                       |
| TAB-14 | Handle rapid switching and asynchronous results.                                     | A response for a previously selected tab does not overwrite the current panel or appear under the wrong label.                                                                                                                 |
| TAB-15 | Make unavailable tabs understandable when present.                                   | Disabled appearance and behavior agree; the reason is discoverable when not evident. Conditional hiding or disabling is chosen intentionally.                                                                                  |
| TAB-16 | If counts or badges appear, define their meaning and freshness.                      | Counts are associated with the right labels, do not crowd them, and unknown/loading values are not falsely displayed as zero.                                                                                                  |
| TAB-17 | If views are addressable, define URL, refresh, and history behavior.                 | Direct links and Back/Forward restore the intended view; do not require a browser-history entry for every local tab change unless the workflow needs it.                                                                       |
| TAB-18 | If tabs can be closed, define selection and focus after removal.                     | Closing the active tab chooses a logical remaining view or fallback and does not silently lose unsaved work.                                                                                                                   |
| TAB-19 | Verify applicable states and user journeys.                                          | Check keyboard and touch, long labels, overflow, zoom, narrow layouts, loading/error/empty states, rapid switching, return to an earlier panel, and relevant refresh or history behavior. Record unverified checks accurately. |

## Status filters and content switching

All / Active / Archived often changes which records appear in a single result area. It may look like tabs, but its selection model and accessible semantics must match the actual behavior. A content switcher, radio-style choice, or filter control may be more appropriate than a true tab-and-panel pattern. A product with genuine panels can still use tabs. Do not treat a design-system-specific recommendation as a universal ban.

| ID        | Guideline                                                  | Verification                                                                                                                                                    |
| --------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FILTER-01 | Decide whether the filter allows one status or several.    | The selection model and semantics match; a single-selection control does not imply multi-selection.                                                             |
| FILTER-02 | Expose the selected condition and its result clearly.      | The selected status matches the records; changing a filter is not merely a styling change.                                                                      |
| FILTER-03 | Define interaction with search and other filters.          | Switching status preserves or resets other criteria intentionally; All means all statuses within the stated scope, not necessarily clearing every other filter. |
| FILTER-04 | Define count scope when showing counts.                    | Users can understand whether counts include current search/other filters, the full dataset, or another stated scope; result totals are consistent.              |
| FILTER-05 | Keep pagination and selection valid after a filter change. | A narrower result set does not leave users stranded on an invalid page; selected records and bulk-action scope are handled explicitly.                          |

| FILTER-07 | Verify result correctness and response ordering.           | Search-plus-status combinations, zero results, repeated changes, and slow responses do not display stale records under the current selection.                   |

Routing: for true tabs select Tabs and related views, Accessibility, Responsive design, Spacing and layout, and Feedback and recovery. ## Overlays: modals and drawers

An overlay's placement does not determine modality. A drawer may be modal or non-modal. A portal is an implementation mechanism for rendering content elsewhere in the DOM, not a visual interaction pattern or a substitute for dialog accessibility. Do not require portals universally; a suitable platform or existing component can provide the needed behavior differently.

Before building, select the pattern, decide modality, and specify opening, dismissal, scrolling, unsaved changes, action states, and responsive presentation. Apply Forms when the overlay collects data, plus Responsive design, Accessibility, Spacing and layout, and Feedback and recovery as relevant.

| ID         | Guideline                                                                                                                                                                                    | Verification                                                                                                                                                                            |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OVERLAY-01 | Choose an overlay when a focused temporary task benefits from keeping page context. | OVERLAY-02 | Explicitly distinguish modal and non-modal behavior.                                                                                                                                         | Modal background content is unavailable for interaction; a non-modal drawer preserves a usable way to interact with the page.                                                           |
| OVERLAY-03 | Provide a clear title, readable content, and understandable primary and secondary actions.                                                                                                   | The user knows what opened, what to do, and how to leave.                                                                                                                               |

| OVERLAY-05 | Return focus to the trigger or a logical next workflow target after closing.                                                                                                                 | Keyboard users do not lose their place, including when the original trigger no longer exists.                                                                                           |
| OVERLAY-06 | Match accessible names and semantics to actual behavior.                                                                                                                                     | Assistive technology recognizes the dialog and its name; an overlay is not marked modal while leaving the background interactive.                                                       |
| OVERLAY-07 | Provide a discoverable, keyboard-operable close or cancel route. ## Data tables

Design for the actual task: scanning, comparing values, finding a record, or taking an action. A basic table does not automatically need sorting, search, filters, selection, pagination, or export. Add these only when useful for the task and dataset. Do not prescribe universal column widths, row heights, or padding values; reuse product definitions and verify readable, usable results.

| ID       | Guideline                                                                              | Verification                                                                                                                                                                                                          |
| -------- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| TABLE-02 | Provide clear table context and column headings.                                       | Users know what records are shown and what each value means; units, currency, and date context are explicit where needed.                                                                                             |

## Animation and motion

Decide whether motion is useful before choosing an effect. Motion should support task feedback, state recognition, spatial understanding, or explanation. A static or immediate state change is a valid result. Do not prescribe universal durations, easing curves, spring settings, distances, or animation-library choices. Reuse suitable existing motion conventions and adjust deliberately for the interaction and frequency of use.

### Before building

Identify the purpose, trigger, frequency of use, states, entry/exit behavior, interruption behavior, reduced-motion alternative, and any accessibility criteria. Select the simplest suitable implementation and relevant component guidelines. Decorative motion is optional; it must not obstruct task content or become a prerequisite for using the UI.

| ID        | Guideline or requirement                                                  | Verification                                                                                                                                                                                                                                                                                                          |
| --------- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| MOTION-01 | Give motion a clear purpose, or omit it.                                  | It communicates feedback, a change, a relationship, or a useful explanation rather than adding repetitive distraction.                                                                                                                                                                                                |
| MOTION-02 | Match intensity and duration to task frequency and context.               | Frequently repeated interactions stay responsive and unobtrusive; occasional expressive motion does not block work. No numeric timing is imposed.                                                                                                                                                                     |
| MOTION-03 | Preserve immediate feedback and access to the task.                       | Users need not wait for decorative sequences before reading content, activating controls, or moving on.                                                                                                                                                                                                               |
| MOTION-04 | Keep motion consistent with the interaction and spatial relationship.     | Drawers, anchored popups, expanding sections, and changing views move or transition in understandable ways, not arbitrary directions.                                                                                                                                                                                 |
| MOTION-05 | Reuse suitable motion conventions and animate only intended properties.   | Similar interactions feel coherent; unrelated style changes do not start unexpected transitions.                                                                                                                                                                                                                      |
| MOTION-06 | Support interruption, reversal, and repeated activation.                  | Open-close-open, rapid toggling, repeated tab changes, and interrupted gestures leave the correct final state without jumps, queued obsolete motion, or trapped UI.                                                                                                                                                   |
| MOTION-07 | Coordinate motion with actual UI state and focus.                         | Entering/exiting overlays maintain correct focus and background behavior; elements that look gone do not retain unintended interaction, and exit effects do not leave focus stranded.                                                                                                                                 |
| MOTION-08 | Preserve stable reading and interaction targets.                          | Text and important data do not move for decoration while being read; insertion or removal avoids confusing jumps and moving controls under a pointer.                                                                                                                                                                 |
| MOTION-09 | Respect reduced-motion preferences from the outset.                       | Remove or replace non-essential translation, scaling, parallax, and repeated movement as appropriate, while preserving feedback and access through instant changes, text, or suitable gentle alternatives. Do not assume a shorter animation alone is sufficient.                                                     |
| MOTION-10 | Provide appropriate control over qualifying automatic motion and updates. | Apply WCAG 2.2 SC 2.2.2: automatically starting moving/blinking/scrolling content lasting more than five seconds alongside other content has pause/stop/hide unless essential. Qualifying auto-updating content also permits pause/stop/hide or update-frequency control; it does not have the five-second exception. |
| MOTION-11 | Avoid flashing effects and verify applicable flash safety requirements.   | Meet WCAG 2.2 SC 2.3.1: no more than three flashes in any one-second period, or below the defined general/red flash thresholds. Merely averaging the flash rate is not verification. Omission of flashes is preferred.                                                                                                |
| MOTION-12 | Do not convey essential meaning through motion alone.                     | State, status, progress, and outcomes are also understandable through appropriate text, semantics, or static cues.                                                                                                                                                                                                    |
| MOTION-13 | Keep loading and progress feedback truthful.                              | Indeterminate animations indicate waiting rather than invented completion; actual progress is based on real information, and failure or timeout has an appropriate recovery path.                                                                                                                                     |
| MOTION-14 | Adapt to input methods and viewports.                                     | Hover effects do not become stuck or essential on touch; responsive changes do not move content off-screen or lose state. Gesture-only actions have suitable alternatives.                                                                                                                                            |
| MOTION-15 | Choose efficient properties and implementation, then measure.             | Prefer transform/opacity where they fit; layout animation such as expanding height may be justified. Do not assume any property or tool guarantees GPU execution or smoothness. Check frame behavior and responsiveness under relevant load.                                                                          |
| MOTION-16 | Keep decorative sequences and continuous loops proportionate.             | Staggers, page reveals, and looping effects do not delay important information or repeatedly restart during ordinary use. Content stays accessible if effects cannot run.                                                                                                                                             |
| MOTION-17 | Check readable content and applicable contrast during meaningful states.  | Moving backgrounds, fades, and overlays do not leave important text or controls unusable; apply Color contrast and Typography as relevant.                                                                                                                                                                            |
| MOTION-18 | Verify actual playback, accessibility alternatives, and final states.     | Test entry/exit, repeated activation, interruption, slower devices or busy loading, reduced motion, keyboard/touch, small screens, long content, and failures. A static mockup or declared duration alone does not prove animation quality.                                                                           |

### Component-specific direction

- Buttons: subtle feedback when useful; no decoration that delays activation.
- Modals and drawers: movement can communicate appearance and location; focus and dismissal remain correct during transitions.
- Tabs and filters: a selection indicator may transition, but selected state and content must remain accurate during rapid changes.
- Accordions and expanding content: preserve grouping and access while the layout changes; clip neither content nor focus.
- Tables and charts: prioritize stable reading and comparison; changes must not misleadingly imply data or progress that did not occur.
- Toasts and status messages: understandable entry/exit and repeat behavior; essential information is not available only during a fleeting animation.
- Landing/onboarding content: expressive motion may explain or support the experience, with task access, reduced motion, and automatic-motion controls where applicable.

WCAG level distinction: SC 2.2.2 and SC 2.3.1 are Level A and part of an AA conformance target. SC 2.3.3 Animation from Interactions is Level AAA; honoring reduced-motion needs is included as this library's design guidance without mislabeling that criterion as AA. Contrast and motion checks alone do not establish full WCAG conformance.

References: [W3C: Animation from Interactions](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html), [W3C: Pause, Stop, Hide](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html), [W3C: Three Flashes or Below Threshold](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html), [web.dev: High-performance CSS animations](https://web.dev/articles/animations-guide).

## State management and code organization

Library-selection policy: use an external state-management library rather than relying on framework built-in methods as the application's state-management solution. If another library is explicitly requested or specified, follow it. Otherwise default to Redux, using modern Redux Toolkit and React-Redux integration for React applications. This is a project preference, not a claim that every application universally needs Redux. If the platform cannot support the default, identify that constraint and use an explicitly suitable external alternative rather than pretending Redux was applied.

TanStack Query and RTK Query primarily manage server-data queries and their cache; they are not interchangeable with every client-state need. Default client application state remains Redux unless an alternative is specified. With Redux, RTK Query is the default server-data integration direction when queries are needed. An explicitly selected TanStack Query can own the server-data cache. Do not introduce both query systems for the same resources merely to satisfy a checklist.

### Before implementation

Inventory the state, its owner and scope, lifecycle, updates, derived values, server-query needs, and freshness requirements. Identify the selected external library and any explicit existing architectural constraints. Define feature boundaries and choose which components subscribe to which values.

| ID       | Requirement or guidance                                                                             | Verification                                                                                                                                                                                                    |
| -------- | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| STATE-01 | Apply the external-library policy and Redux default.                                                | The application state has an identified external owner; framework built-ins are not quietly substituted as the main architecture. An explicit alternative takes precedence.                                     |
| STATE-02 | Classify client UI state, shared domain state, server data, URL state, and derived data separately. | Each value has an authoritative owner; routing/query parameters and server-cache results are not needlessly duplicated in a client slice.                                                                       |
| STATE-03 | Keep state scoped to the feature or interaction that needs it.                                      | External-library use does not imply every value should be subscribed to globally. Per-instance forms, panels, and drafts do not interfere with each other.                                                      |
| STATE-04 | Store only necessary source state and derive other values appropriately.                            | Counts, filtered lists, and computed totals do not become separate copies requiring error-prone synchronization. Memoized derivation is added where useful.                                                     |
| STATE-05 | Make state transitions explicit and coherent.                                                       | Idle, loading, success, failure, and selected/open states reflect actual operations; conflicting combinations do not arise from unrelated duplicated flags.                                                     |

| STATE-07 | Keep application Redux state serializable and appropriate to its purpose.                           | DOM nodes, functions, promises, and other runtime resources are not stored as ordinary application data.                                                                                                        |

## Rendering performance

The rendering goal is to avoid unnecessary re-rendering. Required re-renders must remain: changed data, loading feedback, errors, selection, and input need to be reflected in the UI. Zero re-renders is neither the target nor a truthful promise. A selector-driven render can also occur through parent changes, context, or component-local behavior; do not imply a state library eliminates all rendering.

| ID        | Guideline                                                                                     | Verification                                                                                                                                                                            |
| --------- | --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RENDER-01 | Subscribe to the smallest relevant state or query result.                                     | Updating one feature does not cause unrelated subscribed components to render simply because they read the whole store.                                                                 |
| RENDER-02 | Keep selector results and props stable when their meaningful values have not changed.         | Newly allocated objects/arrays or callbacks do not defeat useful equality checks on every unrelated update.                                                                             |
| RENDER-03 | Update only the records and branches that changed.                                            | Unaffected data retains useful identity; lists have stable keys and record-level subscriptions where appropriate.                                                                       |
| RENDER-04 | Keep frequent updates close to their consumers.                                               | Typing, pointer movement, or streaming updates do not unnecessarily refresh the whole page; global dispatch and subscriptions are deliberate.                                           |
| RENDER-05 | Use memoization and component boundaries where they address measured or well-understood work. | Do not blanket-wrap every component or calculation; optimization preserves behavior and has a demonstrable benefit.                                                                     |
| RENDER-06 | Use debouncing, throttling, pagination, or virtualization only where the task benefits.       | Input remains responsive, relevant results stay current, and essential immediate feedback is not delayed.                                                                               |
| RENDER-07 | Measure realistic interaction cost.                                                           | Profile relevant journeys such as typing, filtering, selecting a row, changing tabs, and unrelated state updates; record causes and improvements without arbitrary render-count limits. |
| RENDER-08 | Distinguish development behavior from a production performance defect.                        | Development diagnostic renders are not automatically called regressions; production-relevant cost and UI correctness are checked before optimizing.                                     |

## Caching and server data

Cache where reuse benefits the task and freshness rules permit it. Avoid caching or reusing stale data where correctness requires a fresh result. A query cache, computation memoization, and persistent browser storage are different mechanisms; one does not automatically justify another. Do not prescribe one global cache lifetime, persist all state, or disable every cache indiscriminately.

| ID       | Guideline                                                                | Verification                                                                                                                                                                                                                               |
| -------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| CACHE-01 | Assign one authoritative query-cache owner per resource domain.          | RTK Query or the explicitly chosen query library owns fetching, pending/error state, and reuse; UI slices do not maintain competing copies of the same server results without a documented purpose such as an editable draft.              |
| CACHE-02 | Identify reuse and freshness needs per resource.                         | Slowly changing reference data, fast-changing operational data, and one-off operations have intentionally different policies.                                                                                                              |
| CACHE-03 | Include all result-changing inputs in query identity.                    | Search, filters, sort, pagination, record identity, and applicable account/tenant context cannot accidentally reuse another query's data.                                                                                                  |
| CACHE-04 | Define freshness, inactive retention, and persistent storage separately. | A retained result is not assumed fresh; cache eviction and browser persistence do not silently replace freshness checks.                                                                                                                   |
| CACHE-05 | Invalidate or update affected cached data after mutations.               | Create/edit/delete and bulk operations update or refetch relevant detail views, lists, counts, and filtered results.                                                                                                                       |
| CACHE-06 | Define automatic refresh intentionally.                                  | Focus/reconnect refetch, polling, subscriptions, and background refresh follow the task's freshness needs instead of unexplained library defaults.                                                                                         |
| CACHE-07 | Prevent stale request and optimistic-update defects.                     | Rapid input changes and overlapping requests preserve current selection; optimistic failure rolls back or reconciles appropriately.                                                                                                        |
| CACHE-08 | Avoid reusing cached decisions where an authoritative check is required. | Actions such as a consequential submission obtain required current server validation; cached displays do not authorize or guarantee a transaction outcome.                                                                                 |
| CACHE-09 | Clear or partition user-dependent caches correctly.                      | Logout, account changes, and tenant changes cannot display another session's records. Credentials are not cached or persisted as ordinary data.                                                                                            |
| CACHE-10 | Distinguish a short-lived draft from a server-data cache.                | A draft has deliberate save/reset behavior and does not become a second authoritative server record. Sensitive fields are kept out of general shared persistence and routine debug/log output.                                             |
| CACHE-11 | Avoid unnecessary caching and duplicate fetch mechanisms.                | One-off values or cheap derivations do not acquire complicated invalidation without benefit; duplicate subscriptions, effect-based fetches, and query libraries do not issue redundant requests for the same intended operation.           |
| CACHE-12 | Verify cache behavior using actual requests and state.                   | Check first load, revisit, changed query inputs, stale refresh, mutation, error/retry, concurrent requests, and relevant account changes. Record hits/refetches and invalidation evidence; do not claim network behavior from screenshots. |

## API requests and integration

API integration policy: keep API code separate from UI code; choose suitable query/state integration for the stack, prefer Axios as an HTTP client when appropriate, and avoid unnecessary requests, duplicated state, and unrelated renders. Axios is a preference, not a requirement to replace an already suitable transport. Library choice can be clarified with the user when the actual project context leaves a material choice unresolved; do not ask repeatedly when the stack or earlier decision already resolves it. For an unspecified stack, retain the established Redux Toolkit default and use RTK Query for server-data integration when applicable. The Redux Toolkit query system is named RTK Query, not Redux Query.

Axios sends HTTP requests. RTK Query or TanStack Query coordinates query identity, server data, request state, cache, and invalidation. These are complementary responsibilities, not competing names for the same layer. With Redux, RTK Query may use its existing base transport or an appropriate shared Axios-backed base query; with TanStack Query, query functions can call shared Axios service functions. Avoid installing or combining redundant clients and query systems merely to satisfy a checklist.

### Responsibility boundaries

| Layer                        | Owns                                                                                           | Does not duplicate                                                           |
| ---------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| HTTP client                  | Relevant service configuration, headers, timeouts, transport, and shared error/auth handling   | UI-specific state, component rendering, or a second unmanaged response cache |
| Feature endpoints/services   | Resource operations, request parameters, response transformation, and contract boundaries      | Screen layout and unrelated feature logic                                    |
| Query integration            | Query identity, cached server data, request lifecycle, refresh/invalidation, and subscriptions | A competing copy of the same authoritative data in an ordinary UI slice      |
| Hooks/adapters, where useful | Component-facing query use, selected results, and reusable feature behavior                    | A new generic wrapper that reimplements the chosen query library             |
| UI                           | Rendering relevant data and states, collecting user intent, invoking actions                   | Scattered raw transport calls and ad hoc global caching logic                |

Hooks are a suitable React integration point when the query library provides them or when a focused reusable feature hook helps. Plain service functions remain appropriate for framework-independent operations, jobs, and non-component consumers. Do not require every API function to be a hook, call hooks outside their supported context, or force extra wrappers around simple generated query hooks.

### Before implementing

Identify existing transport and query libraries, the endpoint contract, the operation's trigger and prerequisites, server-data ownership, query identity, freshness/retention needs, mutation effects, error/retry strategy, and expected UI states. Select API requests and integration, Caching and server data, State management and code organization, and Rendering performance, alongside relevant UI categories.

| ------ | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API-01 | Choose libraries according to the explicit stack and prior decisions.                 | Redux integrates with RTK Query when suitable; TanStack Query is used when selected. ### Cache direction examples — contextual, not fixed rules

- Repeated reads of slowly changing reference data: reuse can help; define how changes become visible.
- Lists and record details: reusable cache can help navigation; keys and post-mutation invalidation must be correct.
- Fast-changing status: shorter acceptable staleness, deliberate refetch/polling, or live updates may be needed; no fixed lifetime is imposed.
- Consequential writes and authoritative validation: do not replace the server operation with a cached result or automatically replay unsafe writes.
- Sensitive or session-specific data: scope reuse deliberately; no blanket persistence and no cross-account reuse.
- One-off results with no meaningful reuse: avoid adding cache/invalidation complexity without benefit.

### After implementing

Record the chosen transport and query owner, feature boundaries, query inputs, cache/freshness policy, mutation invalidation, and verification evidence. Confirm both UI correctness and request behavior. Necessary refetches and re-renders are not failures; unexplained duplicates, stale responses, stale cache after mutations, and unrelated render work are defects to resolve.

## Progressive web apps (PWA)

Treat a PWA as a usable web application with progressive capabilities, not just a manifest, icon, or install button. Explicit policy: offline mode and PWA-specific caching are disabled by default. Enable offline content, service-worker response caching, precaching, offline persistence, queued offline writes, or background synchronization only when the user explicitly requests or specifies them. Do not infer that requesting a PWA authorizes these features. Installation, push, and background capabilities differ by browser and platform; detect relevant support and preserve a usable browser experience.

This PWA policy governs app-added offline and persistent caching behavior. It does not by itself disable ordinary browser HTTP caching or an intentionally chosen in-memory API-query cache; those remain subject to the separate API and caching policies. It does not authorize adding persistence to a query cache. Do not claim all cache layers are disabled merely because PWA caching is disabled.

Checks that concern offline caches, persisted offline data, queued writes, synchronization, or a caching service worker are conditional on explicit user authorization. When these capabilities are off, mark those checks Not applicable and verify their absence. Network-failure feedback and ordinary browser usability still apply.

### Before building

Define supported environments, install experience, and update behavior. Record offline mode and PWA caching as Off unless explicitly requested; if requested, define offline task scope, cache boundaries, user/account data policy, and any pending-write synchronization. Reuse suitable project tooling rather than requiring one universal PWA library. Apply Responsive design, Accessibility, Color contrast, Typography and content, Navigation, State management, API requests, and Caching as applicable.

### After building

Record supported and unsupported capabilities, offline/PWA-cache settings, update policy, and verification evidence. Verify defaults remain off when not requested. Conditional offline/cache/sync checks are Not applicable with that reason; ordinary network-failure usability is still checked. If offline features were requested, record their precise scope and resource strategies and verify them. Test intended environments, installed mode, and any applicable worker lifecycle behavior.
